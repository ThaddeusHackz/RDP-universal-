# THADD OS — Final Forensic Scan: "why can't I log in with the RDP credentials?"

**Scan date:** 2026-08-19 · **Scope:** entire tree + CI history + upstream
xrdp 0.9.19 source (Debian 12's exact package) + deployed-environment gap
analysis · **Predecessors:** [`RDP_LOGIN_FORENSICS.md`](RDP_LOGIN_FORENSICS.md)
(findings 1–10, fixed), [`FORENSIC_SCAN_CURRENT.md`](FORENSIC_SCAN_CURRENT.md).

## 0. Executive summary

Every layer of the credential path was re-audited *again*, this time
including the upstream C source of the exact xrdp build the image ships,
the full GitHub Actions history, the CI-captured desktop screenshot, and a
byte-level sweep for invisible defects (CRLF, non-ASCII, trailing
whitespace — none found).

**The in-container login chain is provably sound**: CI run
`32217407378` (main, merge of PR #3) performed a real FreeRDP login whose
proof — a 79 KB screenshot of the rendered XFCE desktop — is committed at
`ci/thadd-os-screenshot.jpg`. PAM accepts the correct password and rejects
a wrong one; sesman spawns Xvnc with a per-session GUID-derived `-rfbauth`
file (verified in `sesman/session.c` + `sesman/env.c` of v0.9.19), so the
RDP session never depended on `~/.vnc/passwd` at all.

The remaining "I still can't log in" surface is the **gap between CI and a
live deployment**. Three defects lived there:

| # | Defect | User-visible symptom | Fix |
|---|---|---|---|
| F-11 | CI never executed `scripts/ci/test_login.py` (the PAM accept/reject gate) — a dead safety net | regressions could ship with a green badge | gate + stale-volume E2E added to the CI suite (`ci/thadd-os-ci.yml.example`; enabling on `.github/workflows/` needs the `workflows` permission — see `ci/ENABLE-CI.md`) |
| F-12 | A Railway volume seeded by an **older broken image** was never healed; a dead `~/.vnc/xstartup` kills the desktop *after* authentication succeeds | "correct password but login fails / black screen" | entrypoint re-installs the session bootstrap + tops up missing skel files on **every** boot; CI plants a stale volume and proves the heal |
| F-13 | No build fingerprint anywhere — a stale (pre-fix) deployment is indistinguishable from the fixed one | "I fixed it but it still fails" | `/etc/thadd-build` stamp baked at image build; exposed via `/api/creds`, `/api/login-status`, `/api/login-probe`, portal footer, `thadd doctor` |
| F-14 | The deployed instance never self-verified that it accepts the credentials; a broken login was **silent** | no way to know *why* | `login-probe` supervised service: pamtester accept **+** reject, listeners, PAM/xrdp.ini/TLS audit every minute → `/api/login-probe` + portal banner |

Composite verdict: **the credentials were (still) never the problem — the
environment around them was.** All four defects are fixed in this tree and
each fix has an automated gate.

## 1. Method

1. **Tree audit, line by line** — Dockerfile, entrypoint, every file under
   `config/`, `web/`, `skel/`, `scripts/`, CI workflow and examples.
2. **Upstream cross-check** — the exact login machinery of
   `neutrinolabs/xrdp v0.9.19` (Debian 12's package) read from source:
   `sesman/session.c` (Xvnc spawn: `-auth`, `-geometry`, `-depth`,
   `-rfbauth <per-session file>`), `sesman/env.c`
   (`env_check_password_file`: SHA1("xrdp_vnc"+guid) → DES3-obfuscated
   rfbauth file `$HOME/.vnc/sesman_passwd-USER@HOST:DISPLAY`).
   Consequence confirmed: RDP sessions authenticate VNC with a
   session-unique password generated by sesman — `~/.vnc/passwd` (synced to
   `THADD_PASSWORD`) matters **only** to the browser/noVNC path.
3. **CI archaeology** — `gh api` over every workflow run since the legacy
   Windows-RDP era; identified which runs were false greens and which
   performed a real login (sesman `login successful` + ≥8 KB screenshot).
4. **Photographic evidence** — inspected `ci/thadd-os-screenshot.jpg`
   (real rendered desktop: panel, conky HUD, Plank, wallpaper).
5. **Invisible-defect sweep** — CRLF / non-ASCII / trailing-whitespace
   scans of every config and script: clean.
6. **Deploy-gap modelling** — enumerated every difference between CI and a
   live Railway deployment (volume, rebuild timing, TCP proxy, real
   clients) and attacked each.

## 2. Findings F-11 … F-14 (detail)

### F-11 — dead login gate in CI
`.github/workflows/thadd-os-ci.yml` ran `test_http.py`, `test_rdp.py`,
`rdp-login.sh` — but **never** `test_login.py`, the script whose whole job
is proving PAM accepts the real password and rejects a wrong one.
**Fix:** the CI suite (`ci/thadd-os-ci.yml.example`, promoted to
`.github/workflows/` via `ci/ENABLE-CI.md` — the push token here lacks the
`workflows` permission) now runs a "Login-path gate" step plus the
stale-volume E2E; the gate's `/api/login-probe` checks also cover F-14.

### F-12 — stale persistent volume poisons the session after auth
Railway mounts `/home/thadd` from a volume. The entrypoint seeded fresh
volumes but never *repaired* old ones. Any home seeded by a previously
broken image (this repo shipped several in its history) keeps its stale
`~/.vnc/xstartup`; the browser desktop dies right after a correct VNC
auth, and any RDP session landing on a polluted profile can die the same
way — indistinguishable from "wrong password".
**Fix (entrypoint.sh):** every boot —
`install -m 755 /etc/skel/.vnc/xstartup` (force, OS plumbing), then
`cp -an /etc/skel/. home/` (top up missing, never clobber user data), then
`chown -R` back to the user.
**Proof:** new CI step `scripts/ci/test_stale_volume.sh` plants
`.thadd-seeded` + a broken non-executable `xstartup`, boots a second
container over it, and requires: healed executable xstartup, real shadow
hash, and the instance's own login-probe reporting `ready:true`.

### F-13 — stale deployments are invisible
Nothing identified *which image* a running instance had. If Railway never
redeployed (failed deploy, pinned commit, disabled auto-deploy), users kept
hitting pre-fix code with post-fix expectations.
**Fix:** `RUN date -u …> /etc/thadd-build` at image build; surfaced in
`/api/creds`, `/api/login-status`, `/api/login-probe`, the portal footer
and `thadd doctor`. One `curl` now proves whether the fix shipped.

### F-14 — broken logins were silent
Only CI (never the deployment) proved credentials worked. Now a supervised
`login-probe` service re-proves it **on the instance**, every minute:
shadow hash real, 3389 listening, sesman alive, `pamtester` accepts the
real password *and* rejects a wrong one, no `pam_loginuid required`,
`autorun=Xvnc`, `security_layer=tls`, TLS material present, VNC passwd
present. Verdict + reasons → `/opt/thadd/login-probe.json` → nginx
`/api/login-probe` → portal banner / `thadd doctor`.

## 3. Chain verified (for the record)

```
mstsc / FreeRDP / Remmina
   └─ TLS handshake (security_layer=tls; self-signed cert → one warning)
xrdp :3389 (autorun=Xvnc ⇒ no broken Xorg dropdown)
   └─ libvnc → sesman :3350
xrdp-sesman: PAM service xrdp-sesman
   ├─ auth sufficient pam_unix.so        ← shadow hash (chpasswd at boot)
   ├─ session optional pam_loginuid.so   ← container-safe (was: required)
   └─ spawns Xvnc :10+ with per-session -rfbauth (GUID-derived)
startwm.sh → session.sh → startxfce4 (XFCE + Plank + conky)
browser path: noVNC → websockify → Xvnc :1 (-rfbauth ~/.vnc/passwd synced to THADD_PASSWORD)
```

Every hop above is asserted at boot (`harden-rdp.sh`), every minute
(`login-probe`), on every push (`test_login.py`, `rdp-login.sh`,
`test_stale_volume.sh`), and visually (`ci/thadd-os-screenshot.jpg`).

## 4. Operator runbook (when a human sees a failure)

1. `curl /api/login-probe` — `ready:false` ⇒ `reasons` names the exact hop.
2. `curl /api/creds` — compare `build` with the repo's latest commit date;
   older ⇒ **redeploy**, the instance predates the fix.
3. Native RDP needs Railway **TCP proxy → 3389**; the web domain is HTTP-only.
4. Accept the one self-signed-TLS warning; xrdp's login screen is a US
   keyboard — symbols in passwords can be mistyped by non-US clients.
5. Inside the OS: `thadd doctor`.
